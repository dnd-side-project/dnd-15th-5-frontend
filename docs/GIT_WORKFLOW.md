# Git Workflow

코드 작성 규칙은 `docs/CONVENTIONS.md`를 따른다.

## 1. Commit Convention

커밋 메시지는 다음 형식으로 작성한다.

```txt
<emoji> <Type>: <summary>
```

커밋 메시지 작성 규칙은 다음과 같다.

- 한글로 작성한다.
- 작업 내용을 짧고 명확하게 요약한다.
- 하나의 커밋에는 하나의 작업 단위만 포함한다.
- 제목 끝에 마침표를 사용하지 않는다.
- 제목만으로도 변경 내용을 파악할 수 있도록 작성한다.

예시:

```txt
🔧 Chore: ESLint와 Prettier 설정 추가
📝 Docs: 아키텍처 문서 추가
✨ Feat: 자기소개서 목록 페이지 추가
```

현재 commitlint 설정에서 허용하는 타입은 다음과 같다.

```txt
✨ Feat
🐛 Fix
♻️ Refactor
🔧 Chore
🎨 Style
📝 Docs
✅ Test
🚚 Rename
🔥 Remove
```

## 2. Commit Type

| 타입          | 사용 시점                               |
| ------------- | --------------------------------------- |
| `✨ Feat`     | 새로운 기능 또는 페이지 추가            |
| `🐛 Fix`      | 버그 수정                               |
| `♻️ Refactor` | 동작 변경이 없는 코드 리팩토링          |
| `🔧 Chore`    | 설정, 빌드, 패키지, 아이콘, 이미지 추가 |
| `🎨 Style`    | 스타일 또는 포맷 변경                   |
| `📝 Docs`     | 문서 또는 주석 수정                     |
| `✅ Test`     | 테스트 코드 추가 또는 수정              |
| `🚚 Rename`   | 파일·디렉터리 이름 변경 또는 파일 이동  |
| `🔥 Remove`   | 코드 또는 파일 삭제                     |

## 3. Commit Body Rule

커밋 제목만으로 변경 내용을 충분히 설명하기 어려울 때 본문을 작성한다.

- 제목과 본문 사이에 빈 줄을 넣는다.
- 본문은 한 줄에 최대 72자로 작성한다.
- 본문은 한글로 작성한다.
- 변경 방법보다는 무엇을, 왜 변경했는지 설명한다.

예시:

```txt
📝 Docs: 아키텍처 문서 추가

PRD 이후 구현 기준을 통일하기 위해 레이어별 책임과 라우트 구조를
문서화했습니다. 현재 폴더 구조와 ESLint boundaries 설정을 기준으로
작성했습니다.
```

## 4. Branch Strategy

### Git Flow

| 브랜치       | 역할              |
| ------------ | ----------------- |
| `main`       | 배포 브랜치       |
| `develop`    | 개발 통합 브랜치  |
| `feat/*`     | 기능 개발         |
| `fix/*`      | 버그 수정         |
| `refactor/*` | 리팩토링          |
| `docs/*`     | 문서 수정         |
| `chore/*`    | 설정 및 기타 작업 |
| `release/*`  | 배포 준비         |

### Branch Naming

브랜치 이름은 다음 형식으로 작성한다.

```txt
<type>/<description>-<issue-number>
```

예시:

- `feat/login-ui-10`
- `feat/receipt-create-21`
- `fix/map-marker-32`
- `refactor/login-api-10`
- `chore/eslint-03`

브랜치 이름 작성 규칙은 다음과 같다.

- 영문 소문자를 사용한다.
- 여러 단어는 하이픈(`-`)으로 구분한다.
- 이름 끝에 이슈 번호를 작성한다.
- 한 자리 이슈 번호는 앞에 `0`을 붙여 두 자리로 작성한다.
- `develop` 브랜치에서 새 브랜치를 생성한다.
- 작업이 끝나면 `develop` 브랜치를 대상으로 PR을 생성한다.

## 5. PR Policy

PR 본문은 `.github/PULL_REQUEST_TEMPLATE.md` 형식을 따른다.

PR 제목은 다음 형식으로 작성한다.

```txt
<emoji> [<Type>/#<issue-number>] <summary>
```

예시:

```txt
✨ [Feat/#26] Button 공통 컴포넌트 구현
```

PR 본문에는 다음 내용을 포함한다.

- 연관된 이슈
- 체크 사항
- 작업 내용
- 스크린샷 또는 참고 이미지
- 추가한 라이브러리
- 리뷰 요구사항

작업 내용은 변경 범위에 따라 `###` 하위 제목으로 구분한다.
작업 규모가 작더라도 핵심 변경 단위를 확인할 수 있도록 하위 제목을 하나 이상 작성한다.

문서만 변경한 PR에서는 스크린샷과 추가한 라이브러리 항목을 생략할 수 있다.

## 6. PR Checklist

- 관련 이슈를 연결했는지 확인한다.
- 구현 내용과 PR 설명이 일치하는지 확인한다.
- UI를 변경했다면 스크린샷 또는 영상을 첨부한다.
- 라이브러리를 추가했다면 추가 이유를 작성한다.
- 리뷰어가 중점적으로 확인할 사항을 작성한다.
- 콘솔 로그와 임시 코드를 제거한다.
- 남아 있는 TODO가 있다면 이유와 후속 작업을 설명한다.

## 7. Git Policy

AI 도구는 커밋 메시지와 PR 본문의 초안을 작성할 수 있다.

도구별 Git 작업 범위는 다음과 같다.

- **Codex**: 사용자가 명시적으로 요청한 경우에만 `git commit`, `git push`, PR 생성을 실행한다.
  별도의 요청이 없다면 텍스트 초안만 제공한다.

- **Claude**: 커밋 메시지와 PR 본문을 텍스트 초안으로만 제공한다.
  커밋, 푸시, PR 생성은 사용자가 직접 진행한다.

초안은 다음을 참고해서 작성한다.

````md
커밋 메시지 후보:

```txt
📝 Docs: 아키텍처 문서 추가
```

PR 본문 초안:

```md
## #️⃣ 연관된 이슈

- close #이슈번호

## ✅ 체크 사항

- [ ] UI 동작 및 레이아웃 확인
- [ ] 콘솔 로그 및 에러 없음
- [ ] 기능 정상 동작
- [ ] 팀 컨벤션 확인

## 📝 작업 내용

### 주요 변경

- 작업 내용을 작성합니다.

### 📸 스크린샷

### 📦 추가한 라이브러리

### 💬 리뷰 요구사항

-
````
